Session 46 — 2026-08-20: Closed `tmp/fillrace` — the owner's *"using the fill tool more than once breaks it sometimes … it doesnt bake the first one properly before going to the second"* (device, 2026-08-19). **Their reading was right, and all three of the traced mechanisms were confirmed by tests that fail on the parent commit** (4 tests, 8 assertion failures, red before / green after, verified by stashing the production diff and re-running with a build): **(a)** the first fill was dropped — `commitInteractiveFill` is reached through `beginCanvasEdit` at the top of the *next* `begin*Fill`, and it bailed on `guard cel.fillImage != nil`, which is written by the render's hop to main, so a fill that was already rendered read as "nothing was previewed"; **(b)** the second fill never rendered — the superseded worker re-read `fillPending`, booked `fillRendered` against the new gesture's key, and the new gesture's own worker then found `key == fillRendered` and returned having drawn nothing; **(c)** what it rendered paired the new tap's seed with the *old* session, reference composite and sampled colour, and installed itself anyway because the publish only asked whether *some* fill was active — visible as an empty-lasso's "nothing enclosed" banner landing on a bucket fill that had plainly filled something. Fix: every `begin*Fill` claims a `fillGeneration` under `fillLock` (commit and cancel retire it) and the worker carries an immutable `FillGestureContext` rather than reading `fillGestureSeed`/`fillGestureColor`/the target ids off `fillQueue` — which makes the (c) pairing unrepresentable instead of documented-against; the generation is checked before a key is claimed, before a result is stored and again on main before it is installed, and a superseded worker returns **without** clearing `fillWorkerScheduled`, which belongs to whichever gesture is live (`begin*Fill` always sets it *and* enqueues a worker, so no restart can wedge it). `drainFillWork` now stores each render under the lock the moment it exists so the commit can bake a fill whose pixels are real but have not reached main; an empty lasso stores none, so §7.1's no-undo-entry rule still falls out of the same guard. `beginInteractiveLassoFill` had the identical exposure and is covered. **The interleavings are forced, not raced for** — `fillQueue.sync {}` gives "rendered, not yet published" exactly (an XCTest body owns the main thread, so the hop provably has not run), and a semaphore held on the serial queue orders a superseded worker after the gesture that replaced it; a race test that hopes to lose a race can pass on broken code and fail on correct code.
