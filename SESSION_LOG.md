Session 26 — 2026-08-12: LAYER_COMPOSITING.md phase 5a — Tier 1 blend modes, less the sandwich. BlendMode moved out of LayerFolder.swift into its own file (four-point pbxproj registration, since PaintSoftwareUITests hand-lists its sources) and grew to fourteen separable cases; Layer.blendMode and its manifest field are defaulted, so existing projects and every Layer(...) call site are unchanged. "Clip to below" is deliberately not among them: §7 lists it in Tier 1 while saying it is not a blend but the mask machinery with an implicit source, so building it here would mean building phase 6's mask resolution early to serve one mode and rebuilding it when §6.2's AlphaMask arrives — deferred to phase 6 and flagged, so Tier 1 ships as fourteen modes rather than fifteen. **The headline finding is that CGBlendMode is not the authority.** Sweeping all fourteen over 4096 (colour, alpha) pairs put every mode within one step of the shader except colorDodge, colorBurn and softLight at 141, 249 and 16 — not a rounding regime but a different formula, CoreGraphics implementing the PDF 1.4 originals where the two divisions have no zero-backdrop guard (Color Dodge lifts a black backdrop to white where the modern rule keeps it black) and soft light uses a different D(cb) curve. W3C Compositing Level 1 added the guards and is what Photoshop and CSP do, so those three are hand-rolled on the CPU beside add/subtract/linearLight and the shader is the correct one; §5.1's "byte-for-byte definition of correct" is now scoped to the walk — order, buffers, alpha — and not the blend functions. After the fix, leaf and group sweeps read identical and every mode is within 1, softLight reaching 0 despite its sqrt being the sharpest evidence the diagnosis was right. The Metal backend stopped declining groups that need their own buffer, which phase 4 could survive only while a faded group was the sole trigger. PixelOps.rasterize is memoized on model state — §5.2 names it as the fix for the measured 276 ms snapshot and the sandwich structurally needs it — keyed on cel id, object identity *and* version for both tiers, because a cel id outlives the buffers under it: reopening a project rebuilds every RasterLayerTexture with its counter back at 0 under the same id, so a version-only key would serve pre-edit pixels. **Phase 5 is half done: the compositor blends and the thumbnail proves it, but reconcileLayers still hands Core Animation flat siblings, so a Multiply layer looks normal on the live canvas.** That is §5.2's sandwich and it is all that stands between this feature and being usable. Two worker sessions in isolated worktrees, both needing a fast-forward off origin/main first; the compositor worker hit a usage limit mid-task and its work was recovered uncommitted — its recorded delta table had been written before it could run the sweep and read 2 where the truth was 141, which is why the numbers here are measured. Session 27 — 2026-08-13: LAYER_COMPOSITING.md phase 5b — §5.2's sandwich, so the live canvas finally shows a blended layer. **The product owner scoped it: exact at rest, snaps on lift, not mid-stroke fidelity.** That collapsed the phase from "three views always" into two states — at rest the canvas is one `composite(full)` with every host blanked, byte-identical to the thumbnail and exact for every mode and nesting; only while a dab is down does the below/live-host/above trio take over, with the active layer's own blend and any layers above it rendering Normal until lift. The mechanism is one rule: the active layer's content version is in the invalidation key *only* while no stroke is in progress, which freezes the key for the dab and moves it on lift, so stamping never reaches the compositor (§2). `[RenderNode].split(atLeaf:)` prunes either side of the active leaf keeping an enclosing group's properties on **both** halves — approximate where the group buffers, which is exactly §10 decision 5's "live stroke inside a blended group", and 5b shipped that decision's *fallback* rather than the per-frame subtree recomposite nothing has yet needed. `needsCompositorOnCanvas` is the engage switch and the risk containment: a document with no blend modes and no faded or isolated group keeps Core Animation's flat-sibling path untouched and cannot regress. **Blanking a host is a `CALayer` mask, never `isHidden`** — `hitTest` returns nil for hidden, `alpha < 0.01`, or interaction-disabled views, so a blanked *active* host would have swallowed the first touch of every stroke with no error to show for it, and `UIView.alpha` and `CALayer.opacity` are the same property so neither is an escape; UIKit does not consult masks when hit-testing, and an XCUITest guards it. `CALayer.compositingFilter` was rejected rather than untried: private-ish on iOS, and it would use Apple's blend maths, which phase 5a measured as disagreeing with the spec by up to 249/255 — mid-stroke would not have matched at-rest. Deltas measured and asserted at their values so they fail if the approximation improves *or* worsens: exact case 0 across nine tree shapes, active-layer-own-blend 127, blending-layer-above 127, active layer in a faded group 64 (alpha drifts too, not only colour). Two honest caveats from the split worker: delta 0 holds because the fixtures are opaque — the `above` half quantizes to 8-bit once more than the direct walk, reaching 1 only after four stacked fractional draws — and a *faded group above* the active layer is not covered by the stated exact-case condition either. **Measured rebuild cost, 2048²/six layers/CoreGraphics, warmed, median of nine: snapshot 0.1 ms, three composites ~55 ms.** The snapshot is no longer the expensive half — memoizing `PixelOps.rasterize` (`1e4d7d1`) retired the 276 ms this document had designed around since phase 2 — which makes the off-main rebuild and the show-stale-until-ready structure load-bearing rather than incidental, and more so at 4000².
