Session 51 — 2026-08-20: Closed `tmp/text3` — **Add Text stage 3**, ADD_TEXT.md §3's *"vector layers keep it editable"*. On a raster layer text still bakes; on a vector layer the session now lands a `VectorTextElement` in the cel's display list, saves as itself, reloads as itself, and **re-opens under a tap** — `beginTextSession` asks `topmostText(atCanvasPoint:)` before it places anything, loads the element's own recipe and frame into the draft tier, and `commitInteractiveText` upserts it back **at its own index**. Deleting `Tool.textUnavailableReason`'s `.vector` arm was the whole of the UI change, which is exactly the un-shipping stage 1 planned for. **Four calls worth knowing.** *(1)* `Kind.text` is numbered **below** `.stroke` and a new object is `append`ed rather than inserted: the rawValue governs insertion arithmetic, not z-order, and keeping `.stroke` highest is what makes a brush stroke drawn after an erase still land at the end of the list, above the `.erase` punch `eraseHybrid` *appends*. Number text above strokes and that stroke is inserted **underneath a punch that predates it** and gets eaten by an erase that happened before it existed — the failure is invisible until someone erases, then types, then draws. Text and strokes therefore stack chronologically, and §1's "an erase stroke above a text element already masks it" holds unchanged. *(2)* Undo swaps the **whole `elements` array**, not the `texts` bucket, unlike `registerVectorFillUndo` it is otherwise a copy of: the kind-filtered setters gather their kind back at the first one's index, which is order-stable for a contiguous bucket and not for text, which is interleaved with strokes by construction. *(3)* `TextLayout.draw` went from `private` to internal so the vector flatten reaches the **same rasterizer** the bake and the live overlay use — stage 1's report says the overlay's `UITextView` draws no glyphs for precisely this reason, and a second rasterizer on the vector path is the divergence §2 warns about; `TextMeasure.inkBounds` (measure-only, no context, no image) went beside it rather than into a file of its own, since it is called from inside `VectorCanvas`'s non-reentrant lock on the eraser's garbage-collection path. *(4)* **`isTextEditLive` latches forward, not backward** — the one place the sketch in §4 rule 5 would have been wrong if followed literally. `isSandwichStrokeLive` holds the *previous* pass's content version because a dab publishes nothing; opening a text edit does the opposite (it sets `editingElementID`, which invalidates), so freezing against the previous pass would composite the committed glyphs **underneath the live editor** and the artist would see their text twice. Session 53 — 2026-08-20: Closed `tmp/perf9` — **PERFORMANCE.md item 9, all three stages**, and the answer to the question this repo had carried longest. **(a) The number.** Nobody could say whether tapping a project cost 200 ms or 4 s; PERFORMANCE.md §6 called it *the largest unmeasured quantity in the app* and §2 guessed "1-3 s on a hundred-cel project". `ProjectStore.LoadProfile` splits one `load` into the per-cel decode and `regenerateAllThumbnails()` and carries the cel count, and `testWhatOpeningAMultiCelProjectCosts` writes a 4-layer × 8-cel document at the owner's 2048×1024 with real ink on every cel, saves it and opens it back: **303.6 ms — 207.3 decode, 96.3 thumbnails, 9.5 ms a cel**, so **~0.95 s at a hundred cels** (INFERRED, linear in cel count). **The standing guess was ~3× high**, the same shape of error as the 4K recalibration, and the thumbnail walk turned out to be a third of the wait — which is what made (c) worth building rather than an afterthought. **(b)** `PixelOps.parallelMap` is the one fan-out primitive for the two per-cel walks, which are the *same* walk — `ProjectStore.load` decodes one cel per iteration, `renderSources` rasterizes one — and its doc comment says plainly that it spreads work over cores and does **not** by itself leave the calling thread, because `concurrentPerform` recruits its caller. Leaving main is the separate change: `loadInBackground` splits into a nonisolated `decodeCels` and a `@MainActor` `assemble`, and `GalleryView.open` awaits it. The fan-out is **flat across the whole cel tree, not per layer** (six layers of one cel each would parallelise nothing), and each layer's cels are regrouped by job index rather than completion order — cel order is what `activeCelIndex` scans, and a shuffle would surface as the wrong drawing at a frame much later with nothing tying it to a load. `renderSources` became two passes (model reads on main, rasterizes across cores) and **stays** on the main actor deliberately: a synchronous snapshot is what makes it atomic against the artist's own edits, and suspending mid-walk buys a free main thread at the price of a torn frame. **(c)** The gallery's open no longer waits on thumbnails: cels arrive with `thumbnail == nil` — the placeholder already existed, `TimelineTrackView`'s cell hides its image view when there is none — and `backfillMissingThumbnails()` fills them a layer at a time off main, one relayout per layer rather than thirty-two. It is arranged around a **stale** thumbnail, not a missing one: missing is loud, stale is a picture of the drawing as it was before a stroke, so every install re-resolves layer and cel **by id** and compares a `LayerContentVersion` captured *before* the render. **That capture point is the whole guard** — `Cel.raster` is a class, so a version built from a captured `Cel` at install time reads the live counter through the same object and compares equal to itself no matter what was drawn in between. **MEASURED on a dedicated `perf9-1` simulator, Debug, CoreGraphics, two runs at 79–81% idle with no other `xcodebuild` and no other booted simulator**: open **303.6 → 53.5 ms** (5.7×), thumbnails **96.3 → 0** inline plus 23.8 ms after the canvas is up; decode fan-out 162.0 → 41.6 ms (3.89×) with peak 349 → 373 MB; flatten fan-out 58.9 → 15.0 ms (3.92×). **And `renderSources`' 78.2 ms is now ~22 ms** — re-taking item 4b's table, whose own note asked for exactly that. **The three composites are the control**: `full` 11.0 → 11.4, `below` 6.7 → 6.6, `above` 4.5 → 4.4, unchanged code within 4%, which is what says the before and after machines were comparable and the 3.5× is about the code. 4b stays declined, now because the background rebuild *fits* the 24 fps budget rather than because the saving was small. **Contention is the process lesson and it cost two cycles**: the same test read 303, 448 and 527 ms for the same work depending on what the other three sessions were doing, and a cold-vs-warm gap that is 1.4× on an idle Mac read ~2.2× under load — an early draft of this work wrote that gap into a doc comment as a page-fault finding before a quiet run showed it was mostly the neighbours.
