# PaintSoftware structural audit, 2026-11-17 (read-only, main @ 2c43d296)

Method: graphify orientation, grep and reading. Nothing built or run. Every number labelled MEASURED
was read from the repo's own docs; everything else is INFERRED from code and arithmetic. Iteration
was shallow in places (about 25 minutes). Treat file:line as starting points and confirm before fixing.

Device model used throughout: iPad 9, 3 GiB RAM, so `CompositorBudget.textureBudgetBytes` =
physical/16 = **192 MiB** (Compositor.swift:167) and `UndoBudget.maxCostBytes` = **192 MiB**
(UndoHistory.swift:96). One 5000x5000 RGBA image = **100 MB (95.4 MiB)**.

## Ranked findings

### 1. Every budget is a 192 MiB number, and a 5000-px canvas makes one canvas image half of it
Compositor.swift:167, UndoHistory.swift:96, MaskResolver.swift:412 (a further /8 = 24 MiB),
VectorRenderCache.swift:~60, PixelOps.swift:351.
- Artist sees: at 5000x5000 on the iPad 9 a texture "budget" holds under two canvas-sized images. Every
  feature that gates on `workingBytes <= textureBudgetBytes` silently declines (see #2).
- Why tests miss it: logic tests pass `physicalMemory:` explicitly (a seam) but fixtures are 2048x1024
  (53 uses) and 2048x2048. 4096 appears 27 times and 6000 13 times, mostly in `*Bench` files that the
  fast tier excludes by filename and that carry no gates.
- Fix direction: derive budgets from canvas bytes (N canvas-images) as well as device RAM, and add a
  "5000x5000 on a 3 GB device" scenario that every budget consumer must pass.

### 3. Undo trim can silently delete the whole history, including the step just recorded
UndoHistory.swift:262-270 and :129 `record`.
- `trim()` removes from the front while `total > maxCost`. If one action's `cost` alone exceeds 192 MiB
  (a full-cel fill or move at 5000^2 retains before+after about 200 MB, INFERRED) the loop empties the
  undo stack, the new step included. The artist presses Undo and nothing happens, with no notice. The
  redo stack counts toward `total` but is never trimmed, so it can evict real undo steps.
- Why tests miss it: undo tests use small actions against the 768 MiB default, or use `maxCost:` seams.
- Fix direction: refuse or notify before dropping, keep at least the newest step, trim redo first.

### 4. Canvas size ceiling is tuned to the wrong process's memory
CanvasManager.swift:116-146 (the 1850 MiB reference and 0.63 fraction); the fit is "PERFORMANCE.md
§22.2 graded-document phys_footprint".
- The owner's crash was backboardd at 1,850 MiB: Core Animation `contents` images live in the render
  server and are not in the app's footprint. A fit of the app's own footprint says 6000^2 is fine
  (computed 6000 for iPad 9, INFERRED), which is why 5000^2 can be created and then kills the device.
- Why tests miss it: `phys_footprint` is what XCTest can read; the render server is not measurable
  from the app or the test runner.
- Fix direction: count every canvas-sized `CALayer.contents` image alive at once (hosts x images)
  against an explicit render-server allowance, and cap `maxCanvasExtent` by that.

### 5. Many canvas-sized images installed on the layer tree outside a paced path
- Sites: CanvasView.swift:4168 (onion mask), Views/Canvas/LayerHostView.swift:262 (`contentMaskImage`
  per host, canvas-sized, set per stroke at CanvasView.swift:907 and :2048), LivePicture.swift:187
  (`ink.contents = cel.ink`), WindowSurfaceView.swift:74/256, ShapeOverlayView.swift:296,
  PlacementPreviewView.swift:120 (`UIGraphicsImageRenderer` image to `pictureLayer.contents`).
- The mask handed to `setContentMask` is a canvas-sized `CGImage`; the only dedup is identity
  (`contentMaskImage !== image`), so a fresh mask per stroke begin is a fresh 25-100 MB surface. The
  nov16-surfaces branch covers the main edit/undo path. These sibling paths were not checked there.
- Fix direction: a single `CanvasSurfaceBudget` (count and bytes in flight) that all `.contents =` of
  canvas-sized images go through, with release-before-install ordering.

### 6. `refreshDisplay(waitingForTheRender: true)` blocks the main thread for a full-canvas vector render
StrokeCanvasView.swift:1155-1163, called from :1325 (`beginVectorFloat`, i.e. starting a Move/lasso
move). Calls `vectorCanvas.render()` synchronously on main. At 5000^2 with many strokes this is
seconds of frozen UI at touch-down. Also `ProjectStore.save` snapshot (ProjectStore.swift:~838) does
`makeCopy()` of every vector cel on main; `SaveSnapshot` time is only profiled, never bounded.
- Why tests miss it: UI tests on 2048^2 with a handful of strokes; wall-clock assertions are banned
  from the full suite, so there is no gate.
- Fix direction: show the previous picture and render async, as the non-waiting branch already does.

### 7. Thumbnail and raster paths still compute at canvas size
ThumbnailRenderer.swift:11-16: `raster.renderToUIImage()` builds a canvas-sized image and then
downsizes it. The vector path got `render(resolution:)` (VectorLayer.swift:5708) after a MEASURED
34 ms main-thread resample at 6000^2, but the raster/baked path did not. Runs 400 ms after every edit.
- Fix direction: tile-downsample directly into the thumbnail context.

### 8. Three canvas-sized bitmaps retained per vector cel
VectorLayer.swift:2047 `cachedImage`, :2061 `incrementalBase`, :2078 `regionBase`, plus `reducedRender`.
At 5000^2 one cel can hold 300 MB. `VectorRenderCache` evicts by LRU byte total with a floor so that
"never the one just stored", so five layers all being edited keep five x up to 3 images until the next
render of each. The cache accounting comment itself says the entry limit (12) and byte budget interact.
(Today's branch covers the memo-eviction part; the bases are the separate residue.)
- Fix direction: bases are region-sized (they already carry a region); drop `incrementalBase` after
  each commit when the layer is not the active one.

### 9. Caches with entry counts but no byte bound, or bounds that assume small canvases
- PixelOps.swift:351 `sharedRasterizeEntryLimit = 24` (doc admits 1.61 GB at 4096^2, now byte-capped, but
  the cap is the same 192 MiB so it holds at most 1 canvas).
- OnionSkinSource.swift:1195 `entries`/`order` static dictionary: bounded by `sourceCacheLimit(entryBytes:)`,
  but at Full resolution routes through PixelOps.
- BrushTexture.swift:286/886 static `[Key: CGImage?]` dictionaries: confirm eviction (no byte cap seen).
- ColorWheelsEditor.swift:332 `static var cache: [Int: UIImage]`: unbounded by key space.
- BrushTable.swift:66-67, RasterLayerTexture.swift:205, Compositor.swift:273: static mutable arrays.
- Fix direction: one registered cache type with byte budget and pressure hook (`MemoryPressure` exists
  and is a good pattern; ~5 caches bypass it).

### 10. Rapid-draw/undo risk from the Fill/mend path, beyond what nov16-fill fixes
CanvasManager+Fill.swift:1355 `work: 64_000_000` literal, :1605 `[UInt8](repeating:0, count: width*height*4)`,
LassoFillMask.swift:42/425 allocate a full-canvas buffer per lasso rasterize, and MetalFillEngine.swift:174,
331-366 all return silently on `hasHeadroom` failure. The branch changes the limits; the pattern of
"literal work budget -> nil" remains in VectorMendSupport.swift:412-476, :965.

### 11. Full-canvas CPU buffers allocated per action (counts per second not bounded)
MaskResolver.swift:54/146/239/266 (width*height coverage per alpha-mask resolve, per frame bake),
Compositor.swift:1313, MetalCompositor.swift:1219, RenderRequest.swift:113, PixelOps.swift:633/807,
Engine/FrameBakeStore.swift:521, CelPixelSnapshot.swift:106, MetalEffects.swift:293. None is paced; they
rely on callers being sparse. Rapid input at 5000^2 multiplies them, and the allocator does not return
pages promptly. No test counts allocations per stroke at a real canvas size.
- Fix direction: pool and reuse canvas-sized scratch buffers (a `ScratchPool` with a byte cap).

### 12. The canvas-freeze repair is permanent infrastructure for an unfixed root cause
CanvasView.swift:4472-4663 (`replaceStrandedRecognizers`, `CanvasRepairDeadline`), Debug/CanvasRepairCount.swift,
Debug/FlightRecorder.swift, Debug/WindowEventTap.swift (1017 lines), Debug/ActionRecorder.swift (870), and the
Settings row "Canvas freezes caught: N". It swaps UIKit gesture recognizers on a timer when a touch is
stranded. It is a workaround kept always on, wired into the shipping canvas coordinator. The recorder
ring is bounded (capacity + 90 s window), so growth is fine; the issue is the "freeze" being masked
rather than explained. `Debug/` is 4,700+ lines in the shipping target (UITestSeeds 561, PlaybackProbe 842,
PlaybackTrace 819).

### 13. Test hooks inside production code paths
`Thread.sleep(forTimeInterval: UITestSeeds.slowVectorRenderDelay)` in LivePicture.swift:78 and
StrokeCanvasView.swift:1218, WindowSurfaceView.swift:244, FrameBaker.swift:476. 29 `UITestSeeds.` references
and 33 `CommandLine/ProcessInfo.arguments` reads outside the seeds file. Zero by default, but they are
exactly the kind of seam that diverges the shipped path from the tested one.

### 14. Two or more parallel pipelines for the same job
- Compositing: CoreGraphics `Compositor`, `MetalCompositor`, `StripedComposite`, `ChunkedComposite`,
  `FrameRecipe.compositeBands`, `compositeSplitCel`, selected per tree by `prefersGPUCompositing`
  (Compositor.swift:69, ChunkedComposite.swift:153). Parity is tested by "byte-for-byte" logic tests
  at small sizes (CompositorParityLogicTests); the owner's 2-7 s bakes were in the striped path which
  nobody exercised at 5000^2.
- Mend/fill: `VectorMendSupport`, `MetalFillEngine`, `FillWindow`, `LassoFillMask`, `PixelOps.fill`,
  CPU and Metal variants with separate budgets.
- Rasterise memos keyed on size: `PixelOps.RasterizeKey`, `MaskResolver.CacheKey`, `UploadCache.Key`
  (CLAUDE.md RENDER.md warns these collide for equal-sized buffers).
- Undo: a single `UndoHistory` (good), but `Action` closures capture arbitrary state and `extendLast`
  mutates earlier steps.
- Fix direction: pick a canonical path per job and delete the other, or put one conformance suite at
  5000^2 across all variants.

### 15. Unbounded or weakly bounded timers and observers
`NotificationCenter.default.addObserver` 2 sites versus 5 `removeObserver`; 5 `Timer.scheduledTimer`
(CanvasView.swift:4210, :5243, AutosaveClock.swift:128) and 10 `asyncAfter`. Weak-self hygiene is partial:
104 `[self]`/`self.` closures versus 258 `weak self`. Not individually verified; CanvasView's Coordinator
(about 5,000 lines) is the likeliest holder of a cycle. No leak test at 5000^2.

### 16. Tests that cannot fail or measure the wrong level (CLAUDE.md names these)
- Memory/perf claims on 2048x1024 or 2048^2 fixtures; 5000 and 6000 fixtures exist only in `*Bench` files
  (ThumbnailRenderBench, PlaybackBudgetBench, UndoContentionBench) that are excluded from the fast tier and
  not gated. The very comment at PixelOps.swift:~700 ("never binds on a canvas of 4096^2 or less") documents a
  limit that every fixture sits under.
- 4,790 tests are fast-tier logic tests; XCUITests carry the integration burden and take 76 minutes.
  The suite has no test that draws a stroke on a 5000^2, 5-layer document, undoes it, and asserts a notice or
  render-server bound.
- Fix direction: one device-gated "owner scene" fixture (5000^2, 5 vector layers, heavy brush) required by
  every perf/memory claim; allocation-count assertions rather than wall-clock.

## Verdict
Not spaghetti in the sense of tangled control flow: the design is layered and unusually
documented (pure engine types, an explicit undo stack, a memory-pressure bus, byte-budget caches), and
the failures found are consistent rather than random. The real health problem is concentration and a
single recurring defect class. Roughly 22k lines sit in `CanvasManager`, 6k in `VectorCanvas`, 5k in the
canvas Coordinator, so any cross-feature interaction (undo + fill + layer host + render server) can only
be reasoned about by reading all three. The recurring defect is: a budget or cap is derived from the
device's RAM (192 MiB on the iPad 9) and exercised at 2048-4096 px, then silently returns nil, scales down or
drops history at the owner's 5000^2 scene, and the rest of the system treats that as a normal outcome. Test
coverage is wide (about 5,400 tests) but is logic-tier at small sizes; the only 5000/6000 fixtures are
ungated benches, and render-server memory, the thing that restarted the iPad, is unmeasurable by the harness.
Expect more of the same: every `hasHeadroom(...) else { return nil }` (about 20 sites) is a candidate.
The prose docs (11k lines) record measurements that nobody re-checks at the owner's scene. The highest
leverage fixes are one refusal funnel with notices, a 5000^2 owner-scene fixture that gates every budget
consumer, and counting canvas-sized surfaces handed to Core Animation.
